# Analysis Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An eval bar, best move, main line and replay game review from the built-in engine or any UCI engine.

**Architecture:**
- The core `game/analysis.c` wraps the existing opponent drivers (built-in and UCI) as analysers, and grades moves.
- `search_pv` walks the transposition table.
- The TUI adds an analysis panel, a board tint, `a` and `r` keys, a launcher row and an `analyse` command.

**Tech Stack:** C, ncursesw, `make test`, tmux.

**Spec:** `docs/superpowers/specs/2026-09-27-analysis-design.md`

> Terse by request. The spec holds the API and values.

## Global Constraints

- Zero warnings under `-O2 -Wall`; use `make -B` after a header change.
- Core never includes ncurses. Sparse comments. No attribution trailers.
- Only one built-in search may run at a time: `search.c` has global state.
- tmux: session `dchess-t` with exact targets `'=dchess-t:'`, and a scratch HOME/XDG. Typed commands need `i` first.

## Review Focus

1. **Analysis toggled on while the built-in opponent is thinking, or while `go` runs:** no second built-in search starts, and analysis resumes afterwards. tmux check in Task 3.
2. **Analysing a finished position** (mate, stalemate, or no legal moves): no search starts; the panel shows the result. Tests in Task 2 and tmux in Task 3.
3. **A UCI analysis engine that crashes or is removed from engines.conf:** the panel shows the error, and the game goes on. Test in Task 2 with `fake_uci crash`.
4. **Stepping quickly in a replay while an analysis or review runs:** stale results are dropped by key, with no mixing. tmux check in Task 4.
5. **Undo, new game, and loading a FEN while analysis is on:** the analysis restarts for the new position, with no stale tint. tmux check in Task 3.

### Task 2: Analysers

**Files:** `src/game/analysis.c`, `src/game/uci.c` + `headers/game/uci.h` (`pv`), `tests/fake_uci.c` (`analyse` mode), `tests/test_analysis.c`, `tests/test_uci.c`.

- [ ] **Step 1: Tests.**
  - `uci_info_parse("info depth 5 score cp 35 pv e2e4 e7e5 g1f3")` → `pv_len` 3, `pv[0]` "e2e4".
  - Built-in analyser, 300 ms, start position: polling within 2 s gives a legal `best`, and `line[0]` equals its SAN.
  - A mated position: `analyser_start` returns 0.
  - UCI analyser with `fake_uci analyse`:
    - White to move → `score_cp == 35`, line `e4 e5 Nf3`;
    - after `1. e4` (Black to move, the fake still says cp 35) → `score_cp == -35`.
  - `fake_uci crash` → the poll gives a result with `best == 0` (the error surfaces through the driver as with opponents).
- [ ] **Step 2:** Watch them fail.
- [ ] **Step 3: Implement.**
  - `UciInfo` gains `char pv[8][6]; int pv_len`.
  - The analyser struct holds an `Opponent*`, a kind, `time_ms`, the game copy it started on, and its key.
  - The UCI analyser uses the UCI opponent with a movetime of `time_ms`. It needs the driver's last info: add `int opponent_last_info(Opponent*, UciInfo*)` (it already tracks score for the engine panel; extend it to keep the pv). SAN conversion uses a scratch `GameState` copy.
  - The built-in analyser uses `opponent_builtin(MAX_DEPTH, time_ms, NULL, DIFF_HARD)`. On a result, it calls `search_pv` from the analyser's poll. That is safe: the search thread has finished, and only the TUI thread calls poll.
  - Scores go to White's view, and mates follow the spec.
- [ ] **Step 4:** Run `make -B test`. Commit `feat(analysis): built-in and UCI analysers`.

- [ ] **Step 2: State and driving.**

  - `tui_analysis_tick(state)` runs each loop pass (from `drive_turn`'s caller and from the replay loop):

  - `analyse <builtin|off|name>` sets `analysis_engine`, rebuilds the analyser, and is remembered on the profile, as `book` does.

### Task 4: Replay analysis and game review

**Files:** `headers/game/replay.h` (or `tui.h`), `src/tui/replay_tui.c`, `src/tui/panels.c`, `README.md`.

- [ ] **Step 1:** `a` in replay reuses `tui_analysis_tick`.
- [ ] **Step 2: Review.**
  - A heap `ReplayReview` (spec) belongs to the replay state.
  - `r` starts it: a dedicated review analyser at 300 ms, walking `i = 0..count` over positions made by replaying onto a scratch `GameState`.

  - The command bar shows `reviewing k/n`.
